# 2026-08-02

## For future Claude
Finished the OF/IF Directional Progression Report, then spent most of the day on the incident it caused: its FIRST live run exhausted GCSQL02's tempdb. The lesson is the diagnosis, not the fix - **"it worked once, then never again" means WE ate a shared server resource**, and I called it server-side for three round-trips before Zac's "it's never been an issue before" forced me to actually check.

## Top 3 today
1. Ship the remaining directional-report asks (8-metric table, per-direction Val + %iles, gap-spanning sparklines, MoM colour).
2. Diagnose why every run started failing on tempdb.
3. Fix it in a way that is provably output-neutral.

## Wins
- **The diff harness paid for itself immediately.** `--scope afa`: 6,832 rows both paths, identical row universe, 0 `n_plays` mismatches, **6/7 metrics exact**, `top_speed` at `1.07e-14`. That is the difference between "I think the rewrite is safe" and knowing it.
- `top_speed` being the *only* metric with FP noise is itself a correctness signal - it is the one metric with a `CASE` cap, so SQL and pandas round the last bit differently. The noise landed exactly where theory said it would.
- Zac pushed back on my diagnosis and was right. The reports render great; he called them "fantastic."

## Friction
- **I fixed the wrong axis first.** Memoising the pools cut 16 executions to 5. The failure is **per-execution** - it died on execution #1. Reducing the *count* of a query that fails on its first call cannot help, and I still handed over a runbook saying "re-run it," which burned a cycle.
- **I called it server-side three times.** The honest read was available from the first log: the run that *succeeded* is the one that filled tempdb, because tempdb grows to hold sort spills and does not shrink back. "Worked once, then never" was the tell and I talked past it.
- I also oversold a test - told Zac to run the shape test when the rendered `Val` column already proved the same thing. He asked why, and he was right to.

## Notes & ideas
- **PARKED:** Zac - *"maybe similarly built into a dashboard in the future, but for now these reports are great."*
- Decisions locked: YTD stays first-month-to-now **everywhere** (p1 column, fielder progression YTD Gain) - only the sparkline DOT went month-over-month. Tables carry **both** Lvl and MLB %ile and keep all five columns.
- **Rule candidate, offered but not written:** a brand-new heavy query's first live run can exhaust a shared server resource; the tell is worked-once-then-never-again. Waiting on a go from Zac.
- Month chunking is **1..12 on purpose**, not the Apr-Sep `_MONTHS` list - the old query had no month predicate, so anything narrower silently drops March/October games.

## End-of-day reflection
The technical work was fine. The diagnosis was not, and the pattern is worth naming: when something breaks right after my change, my instinct was to prove my change was innocent - and mechanically it *was* - rather than ask what else we had just done for the first time. The report had never run live before that morning. That fact was sitting in my own memory file (`DATA LAYER UNVERIFIED`) the whole time.
