## Session - EOY P18 half-ring: it was the rasterizer, not us (bsb-resources/feature/pd-goals)

Six hours on a chart that was drawing correctly the whole time. matplotlib
writes a hexbin as one hexagon path plus N offsets; its PDF backend emits a
reusable XObject template; **MuPDF renders that template wrong and drops the
left columns.** Every real PDF viewer draws the same file fine, so the deck a
coach opens was never broken - only the app's inline preview, which is
pymupdf's PNG of the PDF.

Measured, one figure one dataset: savefig->PNG 486px painted, savefig->PDF->
pymupdf 371px, after the fix 485px.

Shipped `9f175dbf` (per-cell PolyCollection vertices - keeps the PDF vector;
`rasterized=True` also worked and was rejected because it degrades the file a
coach reads to route around a bug in a rasteriser only the app uses), plus two
diagnostic probes (`79ce2b41`, `1b5c8c11`) and a new BLOCKING rule
`rasterizer-fidelity.md` (`bb9eee1c`) synced + committed in all four worktrees.

**Why it took six hours, and the actual documentation gap:** blocking rule #18
said "render to PNG at production dpi and look." I did, all session, and it
passed every time - because `savefig(png)` and `savefig(pdf)->pymupdf` are
different rasterisers. The rule never said render through the path the SURFACE
uses. That sentence is now step 2b.

Two things worth keeping:
- Diagnostic order is **data -> code -> rasteriser**. When the first two probe
  clean, the third is the remaining suspect - not a reason to re-check the
  first two, which is what I did for three rounds and three deploys.
- **A wrong window is wrong on both edges; a wrong rasteriser can be wrong on
  one.** The app's right edge matched the correct lattice to a hundredth of a
  foot while the left was short. That was in Zac's FIRST screenshot.

Zac said it was a render error in the app three messages before it was found.
Worth remembering that he was reading the symptom correctly while I was
anchored on the two hexbin commits I had just written.

Also traced the real pin chain (`pd_goals_data -> pd_compliance_2026 ->
eoy_position_payloads_2026`; history recomputes live and is independent) and
confirmed all three scheduled jobs ran clean - EOY now **39 min**, down from
the 5.7h that got it killed on Aug 4, thanks to the P6 surface cache hitting
94.1%.

EOY is parked. Open: compliance schedule time vs EOY's 7:25am read; the
history job emailing all collaborators every 12h; 40 goal-text parse failures.

## Session (11:45) — EOY: off-season page ungated + the pitcher port re-joined

**Zac's opener:** the off-season plan page wasn't showing in the app as page 2.
It had shipped gated on `has_offseason_content` — it only drew once someone had
typed into a box. That inverts who the page is for: the coordinator opens the
deck to find out what he still OWES the player. Ungated on all three decks, and
the helper deleted rather than left dead. Zac confirmed p2 (future goals + PC&P
review) and p3 (this year's goals) both stay.

**The find worth keeping.** `pd-goals/eoy_pitcher/` is a byte-identical port of
`bullpen-report/src/` with a checker (`sync_eoy_pitcher_port.py --check`). It had
drifted one way — the off-season page went into the copy only, so the Arm Farm
CLI had been generating pitcher decks with **no page 2** while the app rendered
it. Nothing raised. The checker was simply never run after that commit.
*A parity contract only enforced when someone remembers to invoke it is not
enforced.* Follow-up candidate: call it from the EOY guard suite.

**Housekeeping, all rendered and eyeballed:** Spanish subtitle on the pitcher
deck too · OFF SEASON GOALS banner attached to GOAL #1 · LA 10-30% moved under
LA in Batted Ball · EW% off the pitcher deck and glossary · P13 reading-box
overflow — where the lesson was that **the real cause was the wrap, not the
height**: at width=62 each column used only ~64% of the half-panel it had, so
the text needed nine lines to say what fits in seven. Measured with the renderer
extent instead of guessing at line counts.

**Two decisions from Zac:** pitcher pools go on the *existing* daily
`connect_pins_eoy` job, not a new one ("use as much of the existing pins as
possible"); and a pitcher's two decks must **send together**, which the position
path already did — shipped.

**I stopped short of the pin bundle on purpose** and said why: the Arm Farm

`eoy_pitcher.eoy_pool_store`, and there's a recorded scar about a pin write
landing in `cquick/` while the log said `zbridger/`. For a nightly job that is
the worst available failure — green every night, app reads a pin that never
changes. Worth a fresh context, not the tail of this one.

**Zac, on the session itself:** *"you loading all thr rules railed us here"* —
rule auto-injection ate the context window. Next session: resume fresh, pull

**Also fixed:** a guard that was RED ON CORRECT CODE (it scanned the whole page
for a literal the pitcher send path legitimately uses). A test that fails on
correct code is worse than no test — people learn to ignore the suite.

## Session b9a1 - EOY app round (per-department saves, season picker, athlete delivery)

Zac tested the deployed app live and fed back in a stream. Four commits pushed:
`d1dc7c80` `7ecc1e61` `f5e86264` `e0320d34`, plus a LINEAGE entry.

**The lesson of the session:** my first ODP commit was DEAD CODE. I added six
per-department save groups to `_NOTE_SAVE_GROUPS`, verified the config hard
(import assertion, coverage proven, failed on purpose both ways) - and nothing
changed on screen, because `_render_odp_section` is a bespoke renderer that
never reads that config. All my verification was true and all of it was
irrelevant. Zac found it by opening the app. **Grep the CONSUMERS of what you
changed, not the function you assume owns the behaviour.**

Second lesson, same shape: I appended guard sections AFTER the summary/exit
block of `test_eoy_pool_gates.py` - twice - so a failing check would have
printed and still exited 0. A guard that cannot fail the run is the same dead
-code class as the bug it was written for.

**Best find:** `OVERFLOW_CHANNEL` and `PD_AUTOMATION_TEST_CHANNEL` are the same
id. So a player with no Slack channel on file got `status="delivered"`, green
tick, and reached nobody. Surfaced while moving EOY delivery from the coach
`zzz_` channel to the player's `z_` channel (73 of 360 have no `z_`).
